# Talk to Krishna — Source of Truth & Knowledge Architecture Policy

## Executive Policy
This document establishes the mandatory engineering standards for knowledge storage, retrieval, interpretation, and persona delivery in Talk to Krishna.

Talk to Krishna is a production knowledge and conversation engine grounded in canonical scripture. Hand-authored JSON summaries, fake semantic vectors, mock knowledge dictionaries, and hardcoded character maps are strictly forbidden.

---

## 1. Non-Negotiable Source of Truth Principles

1. **The Canonical Source Corpus is the Authority:** The canonical source remains the original imported source documents (The Complete Mahabharata Volumes 1–12 and verified Bhagavad Gita verses) plus immutable provenance. A database migration, transformation, or generated enrichment must never be mistaken for canonical truth.
2. **PostgreSQL is the Production Knowledge Store:** The operational production knowledge base lives in relational tables with vector and full-text indexes (`mahabharata_chunks`, `mahabharata_child_chunks`, `gita_verses`, `entities`, `entity_mentions`). Hand-authored JSON files are never the canonical authority.
3. **Embeddings are Derived Indexes, Not Source Truth:** Real 768-dimensional BGE embeddings (`BAAI/bge-base-en-v1.5`) serve as mathematical access paths to source chunks. Zero-vector fallbacks and synthetic vectors are strictly forbidden.
4. **Entity Records are Derived from and Linked to Source Evidence:** Characters, places, and weapons are discovered dynamically from corpus text and entity mentions. No developer-maintained character list in TypeScript or JSON is required for retrieval.
5. **Relationships Require Source Support:** Any relationship between characters or events must be grounded in canonical passages with verifiable page and chunk IDs.
6. **Interpretations are Not Source Text:** Philosophical meanings, ethical dimensions, and psychological motivations belong to the Interpretation Engine and must remain strictly distinguished from canonical translation text in data schemas and runtime prompts.
7. **User Applications are Not Source Text:** Practical advice connecting scripture to modern struggles is derived reasoning, not scriptural canon.
8. **LLM-Generated Content is Never Silently Promoted to Source Truth:** Text generated by models or conversational turns must never be written back into canonical source tables as established scripture.
9. **No Developer-Maintained Character List is Required for Factual Retrieval:** Any character—from central figures like Krishna and Arjuna to lesser-known warriors like Shalya, Barbarika, Vikarna, and Satyaki—must be discovered and retrieved through database search (FTS + vector + entity search).
10. **No Developer-Maintained Event List is Required for Factual Retrieval:** Historical episodes are retrieved from the 13,852 source child chunks, not synthetic event catalog entries.
11. **Missing Source Material Must be Reported, Not Invented:** If a Gita verse or Mahabharata passage is absent from the ingested corpus (e.g., reporting 29/700 verified verses), report the exact verified coverage. Never fabricate missing verses using LLMs.
12. **Every Source-Grounded Claim Must be Traceable to Provenance:** Every citation must contain edition, parva, section, page number, chunk ID, and translation provenance.

---

## 2. Dynamic Entity Discovery — Mandatory

The system MUST NOT require a predefined list of Mahabharata characters, places, clans, weapons, sages, kings, queens, warriors, or other entities in application source code.

Entity discovery MUST originate from the ingested corpus and database-backed entity index.

A character does not need to be known to the developers in advance.

Examples include:
- Krishna
- Arjuna
- Karna
- Bhishma
- Draupadi
- Shalya
- Satyaki
- Vikarna
- Barbarika
- Kripa
- Kripacharya
- Ashwatthama
- Ulupi
- Chitrangada
and lesser-known entities present anywhere in the corpus.

The application MUST NOT contain:
```typescript
KNOWN_CHARACTERS = [...]
ALIASES = {...}
CHARACTER_RELATIONSHIPS = {...}
EVENTS = {...}
```
as a prerequisite for factual retrieval.

Application-level aliases may exist only as optional query optimization hints and MUST NOT be required for correctness.

The database/entity index is authoritative for entity discovery.

### Required Query Path:
```
User Query
   ↓
Entity candidate extraction
   ↓
Database entity search
   ↓
Alias/variant resolution
   ↓
Source-mention retrieval
   ↓
Evidence retrieval
   ↓
Reranking
   ↓
Grounded answer
```

The system MUST continue to work when a character is absent from all application JSON files.

## 3. RAG Must Not Become "Semantic Search + LLM"

Retrieval quality is not established merely because a vector search returns text.

The system MUST evaluate:
1. **Relevance:** Exact semantic and lexical match to the user's inquiry.
2. **Source correctness:** Grounding in canonical editions without translation drift.
3. **Context completeness:** Retrieving surrounding passages to prevent deceptive out-of-context quotes.
4. **Entity correctness:** Accurate disambiguation between characters with similar roles or names.
5. **Temporal/narrative correctness:** Preserving chronological and situational fidelity.
6. **Provenance:** Full traceability to volume, parva, section, page number, and chunk ID.
7. **Evidence coverage:** Covering multiple angles for complex inquiries.

For complex questions, the system should retrieve multiple complementary passages rather than several near-duplicate chunks from the same page.

The final evidence bundle must maximize:
$$\text{Relevance} + \text{Coverage} + \text{Source Quality} + \text{Context Continuity} - \text{Redundancy}$$

---

## 4. Interpretation Is Grounded Reasoning, Not Retrieved Fact

The Interpretation Engine may derive:
- Psychological meaning
- Ethical tension
- Dharma implications
- Philosophical significance
- Character motivation
- Strategic reasoning
- Modern-life application

Every factual premise MUST be supported by retrieved source evidence.

The engine MUST strictly distinguish:
- **SOURCE FACT:** What the text says.
- **INTERPRETATION:** What that text may mean.
- **APPLICATION:** How the interpretation may illuminate a user's situation.

The system MUST NOT present an interpretation as if it were a quotation from Krishna, the Mahabharata, or the Bhagavad Gita.
